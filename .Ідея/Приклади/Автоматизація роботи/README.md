# Автоматизація Codex для Windows

Комплект відокремлено у версії проєкту **0.1.55**, 19.10.2026. Він не залежить від Godot, Blender, Docker, сервера гри чи її збережень.

**`reference/` містить точні копії останніх наявних робочих скриптів.** Файли безпосередньо в цій папці — їхній адаптований переносний варіант: спільна конфігурація, окремий стан та імена завдань для кожного проєкту. Поточні оригінали в `tools/` залишені без змін.

Синтаксис переносних PowerShell-файлів перевірено без виконання. Реєстрація завдань, доставка повідомлень, вікно монітора та вимкнення **під час підготовки пакета не запускалися**. Наявність команди `codex queue --thread ... --message ...` підтверджено довідкою встановленого CLI. Новий пакет не слід вважати перевіреним повним запуском лише тому, що його оригінали раніше працювали.

## Що містить кожний файл

| Файл | Призначення |
|---|---|
| `automation.config.psd1` | Публічні налаштування: корінь проєкту, папка стану, назва вікна, префікс завдань, затримки, шлях до Codex і файла повідомлення. Секретів тут бути не повинно. |
| `automation-common.ps1` | Читає конфігурацію, обчислює шляхи та ідентифікатор проєкту для завдань і блокувань. Сам нічого не запускає. |
| `deferred-first.ps1` | Запускає перший одноразовий таймер і видимий монітор. Перед новим відліком зупиняє попередні таймери цієї розмови, чекає звільнення блокувань і прибирає стоп-файл та паузу. Це явний запуск заново. |
| `deferred-cycle.ps1` | Запускає повторюваний таймер і монітор. Типово інтервал — 5 годин. За наявності стоп-файла нічого не запускає. |
| `deferred-launch.ps1` | Реєструє й одразу запускає завдання Windows Task Scheduler від поточного користувача, без підвищення прав. Таймер прихований, монітор видимий. Забезпечує незалежність від термінала, який може закритися. |
| `deferred-resume.ps1` | Виконавець: відлік, пауза, стоп-файл, запис стану, передавання тексту через `codex queue` саме в задану розмову. З `-Repeat` повторює відлік після успішного передавання; після помилки цикл завершується. Зазвичай запускається через обгортки вище. |
| `deferred-monitor.ps1` | Вікно WPF із двома відліками, часом надсилання, станом процесів і кнопками паузи/зупинки. Закриття вікна не зупиняє таймери. |
| `Показати таймери.cmd` | Відкриває лише монітор; новий відлік не запускає. Працює з шляхами, що містять пробіли. |
| `stop-automation.ps1` | Створює стоп-файл для обох таймерів цього пакета в поточному проєкті. Не видаляє файли проєкту й не вимикає ПК. |
| `resume-message.txt` | Текст автоматичного запиту. Редагуйте його під проєкт і свої межі роботи. Типовий текст не дає дозволу на вимкнення ПК і вимагає окремого дозволу на цикл. |
| `shutdown-after-work.ps1` | Окрема команда вимкнення на вимогу власника: типово чекає 45 секунд, потім виконує `shutdown.exe /s /t 0` без `/f`. Таймери самі її не викликають. |
| `codex-limits.py` | Необов’язкова утиліта перевірки лімітів через локальний протокол Codex. Виводить лише використані відсотки, тривалість вікна й час поновлення; не читає файли авторизації. Потрібен Python 3. |
| `.gitignore` | Виключає локальні продукти Python. Папку стану потрібно також виключити в кореневому `.gitignore` проєкту. |
| `.gitattributes` | Зберігає належні перенесення рядків запускаторів та забороняє Git змінювати байти архівних копій, щоб їхні SHA-256 лишалися чинними після перенесення через Git. |
| `reference/manifest.json` | SHA-256 архівних оригіналів для перевірки точності копіювання. Не є цифровим підписом чи доказом успішного виконання. |
| `reference/deferred-*.ps1` | П’ять незмінених джерельних скриптів: перший таймер, цикл, запуск, виконавець і монітор з початковими шляхами. Призначення збігається з однойменними файлами вище. |
| `reference/shutdown-after-work.ps1` | Точна копія початкового окремого скрипта вимкнення. |
| `reference/codex-limits.py` | Точна копія початкової утиліти лімітів. |
| `reference/show-timers.cmd` | Точна копія кореневого `Показати таймери.cmd`, лише з латинською назвою файла. Вона очікує стару структуру шляхів, тому не є запускатором архівної папки. |

## Вимоги

- Windows з Windows PowerShell 5.1, WPF та Task Scheduler. Ці скрипти не є варіантом для Linux/macOS.
- Встановлений Codex CLI з командою `queue` та налаштованим користувачем входом. Програма може використовувати свій штатний вхід, але переносити її токени чи сховище авторизації разом із пакетом не потрібно.
- Відкрита відповідна розмова Codex і працездатний локальний сервіс доставки. Завдання використовують інтерактивний сеанс поточного користувача; вони не є службою для роботи після виходу з Windows.
- Python 3 потрібен лише для `codex-limits.py`.

Команди нижче виконуються **вручну з кореня цільового проєкту**. `ExecutionPolicy Bypass` діє лише для конкретного процесу; змінювати глобальну політику PowerShell не потрібно. Якщо корпоративна політика забороняє Task Scheduler або непідписані скрипти, її слід узгодити з адміністратором ПК.

## Перенесення на інший ПК або проєкт

1. Скопіюйте **всю папку `tools/automation`** у таку саму папку іншого проєкту. Не копіюйте `.runtime`, старі завдання Windows, ідентифікатори розмов чи сховища авторизації. `reference/` можна залишити лише як архів або не переносити для щоденного використання.
2. Відредагуйте `automation.config.psd1`. За розміщення `tools/automation` значення `ProjectRoot = '../..'` уже вказує на корінь цільового проєкту. Для іншого розміщення задайте правильний відносний або абсолютний шлях, наприклад `ProjectRoot = 'D:\work\OtherGame'`. `StateDirectory` має бути відносною папкою всередині цього проєкту.
3. Задайте назву вікна й затримки в секундах. Поточні значення відтворюють останні налаштування: **11100 секунд = 3 години 5 хвилин**, **18000 секунд = 5 годин**. Це затримки, а не достовірний розклад поновлення лімітів.
4. Перевірте `Get-Command codex.exe` та `codex.exe queue --help`. Якщо Codex не в `PATH`, задайте абсолютний шлях до **встановленого `codex.exe`** в `CodexExecutable`. Не підставляйте шлях до токена або файла авторизації. Команда `queue` залежить від версії CLI; якщо її немає, цей механізм доставки не працюватиме без адаптації.
5. Відредагуйте `resume-message.txt`: вимоги, межі лімітів, дозволені дії. Якщо змінили папку пакета або `StateDirectory`, виправте також наведені в цьому тексті шляхи. Не переносіть дозвіл вимкнути інший ПК автоматично: це окреме рішення власника.
6. Візьміть **точний UUID потрібної розмови на цьому ПК**. Усередині контексту Codex може бути доступна змінна `CODEX_THREAD_ID`; у звичайному PowerShell передавайте `-Thread` явно. Не обирайте випадкову «останню розмову» та не шукайте UUID у приватному сховищі авторизації. Якщо інтерфейс не дає UUID, спочатку визначте його доступним у вашому клієнті способом.
7. Додайте `.runtime/automation/` до кореневого `.gitignore` (або вашу папку стану). PowerShell-файли з українськими рядками зберігайте як **UTF-8 з BOM** для сумісності з Windows PowerShell 5.1; `.cmd` — зі звичайними CRLF-переносами.
8. Запускайте перший таймер тільки коли справді хочете скасувати попередній відлік і почати новий. Цикл запускайте окремо лише після погодження автоматичних повторів. Для одного проєкту використовуйте одну розмову автоматизації одночасно: файли стану й пауза/зупинка спільні для цього проєкту.

Перед зміною конфігурації чи тексту повідомлення зупиніть поточні таймери, а після редагування запустіть їх заново: запущений процес уже має попередні налаштування й текст у пам’яті.

Завдання й блокування переносного варіанта мають префікс із коротким хешем абсолютного шляху проєкту. Різні проєкти не повинні блокувати монітори один одного. Після переміщення проєкту на інший шлях старі завдання самі не переприв’язуються: спочатку зупиніть і видаліть їх за інструкцією нижче.

## Запуск і керування

Замість `UUID_РОЗМОВИ` підставте справжній UUID. Наведені команди не потрібно виконувати всі поспіль.

Перший одноразовий запит через 3 години 5 хвилин і видимий монітор:

```powershell
powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\tools\automation\deferred-first.ps1 -Thread 'UUID_РОЗМОВИ'
```

Власна затримка першого таймера, наприклад 60 хвилин:

```powershell
powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\tools\automation\deferred-first.ps1 -Thread 'UUID_РОЗМОВИ' -DelaySeconds 3600
```

Цикл кожні 5 годин (або за `CycleDelaySeconds` у конфігурації):

```powershell
powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\tools\automation\deferred-cycle.ps1 -Thread 'UUID_РОЗМОВИ'
```

Повторне відкриття монітора: `tools\automation\Показати таймери.cmd`. Кнопка «Призупинити» заморожує обидва відліки, «Продовжити» відновлює їх. Кнопка «Зупинити таймери» створює стоп-файл. Вікно можна закрити без зупинки фонового відліку.

Зупинка без вікна:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\automation\stop-automation.ps1
```

**Стоп-файл не відкликає повідомлення, уже передане в Codex, і не зупиняє розробку, яку агент уже виконує.** Для цього дайте команду зупинки в самій розмові. Відновлення після повної зупинки: явний новий запуск `deferred-first.ps1`. `deferred-cycle.ps1` сам стоп-файл не прибирає.

Перевірка лімітів, коли вона потрібна:

```powershell
python .\tools\automation\codex-limits.py
```

Поле `usedPercent` — **використаний** відсоток, залишок дорівнює `100 - usedPercent`. Вікна визначайте за `windowDurationMins`, не вважайте назву `primary` незмінною гарантією п’ятигодинного ліміту. За помилки мережі, відсутності підтримки протоколу чи невідомих залишків утиліта завершується з помилкою; вигадувати відсотки не можна. Вона не є автоматичним запобіжником таймера — перевірка та рішення залишаються в інструкціях агенту.

Окреме вимкнення **лише за дорученням власника**:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\automation\shutdown-after-work.ps1 -DelaySeconds 45
```

Це закриє поточну Windows-сесію, тому спочатку збережіть роботу. Без `/f` програми можуть затримати або заблокувати вимкнення через незбережені дані. Скрипт не містить примусового обходу такого блокування. Поки йде початкова затримка, запуск у власному терміналі можна перервати `Ctrl+C`. Стоп-файл таймерів **не скасовує** цей окремий скрипт вимкнення.

## Стан, обмеження та видалення завдань

У налаштованій папці стану з’являться `first.json`, `cycle.json`, `monitor.json`, а також службові маркери `pause` та `stop`. Файли стану містять час, PID і технічний статус, а не токени. Це не архів переписки. Не копіюйте їх для перенесення налаштувань.

ПК має залишатися ввімкненим. Скрипт не вмикає ПК, не встановлює будильник виходу зі сну й не продовжує роботу після перезавантаження автоматично. Після сну передавання можливе лише після пробудження; тривалий сон може вичерпати відлік. П’ятигодинний інтервал рахується від успішного передавання запиту, а не від завершення роботи агента.

Очікування виконує PowerShell, без звернення до моделі щосекунди. Передані запити та подальша робота агента використовують звичайні ліміти сервісу. Сам таймер не знає, чи агент ще зайнятий, тому час нового повідомлення не є дозволом запускати паралельну сесію. Помилка `queue` зупиняє цикл без нескінченних спроб. Стан «Запит передано» означає прийняття команди доставки, а не підтвердження завершення роботи агентом.

Для остаточного видалення **завдань цього переносного пакета** після зупинки таймерів виконайте вручну в цільовому проєкті:

```powershell
. .\tools\automation\automation-common.ps1
$automationContext = Get-AutomationContext
$automationTasks = Get-ScheduledTask -TaskName ($automationContext.TaskPrefix + '-*') -ErrorAction SilentlyContinue
$automationTasks | Stop-ScheduledTask
$automationTasks | Unregister-ScheduledTask -Confirm
```

Це не видаляє старі завдання `ScrapHunterMan-Deferred-*` із початкового комплекту. Не запускайте одночасно старий і переносний комплекти для однієї розмови. Старий стан — `.runtime/deferred`, новий типовий стан — `.runtime/automation`; кнопки нового монітора не керують старими таймерами. Видаляти або переналаштовувати старі завдання слід окремо свідомим рішенням власника.
